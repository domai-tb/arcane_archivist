# Arcane Archivist Living Spec - 0.1

## Goals

- Deliver the first playable slice: launch, hub interaction, dungeon dive, reward return.
- Prove the core hybrid loop at minimum scale: library management, top-down procedural exploration, and insight-card action.
- Keep the systems data-driven enough to grow into cards, relics, rooms, and procedural templates later.
- Defer base defence, meta currency, difficulty curses, narrative branching, co-op, and modding tools.

## Player Experience

- The player starts in a small arcane library as the magical librarian.
- A visitor request asks for one forbidden tome from the labyrinth below.
- The player inspects the request, starts a dive, explores a short dungeon, uses a small insight deck to survive, retrieves the tome, and returns to the library.
- The returned tome satisfies the request and is placed in the archive, visibly completing the loop.
- The slice should feel like a tiny but real game: choose to dive, take risks, use cards deliberately, collect a reward, and see the library state change.

## Systems

- Library hub:
  - One playable library room with an archive shelf, request desk, and dungeon entrance.
  - One active visitor request with clear objective, reward text, and a simple urgency indicator.
  - Archive shelf records the recovered tome after a successful run.
- Dungeon dive:
  - One short procedural floor assembled from reusable room templates.
  - Required room types: entrance, two encounter rooms, one reward room, one exit/tome room.
  - Basic enemies, hazards, and pickups sufficient to make movement and card use meaningful.
- Insight cards:
  - Fixed starter deck with movement, offence, and defence utility.
  - Cards have cost, effect text, cooldown or draw cadence, and visible ready/unready state.
  - Card effects can damage enemies, block or avoid damage, and interact with simple dungeon objects.
- Run outcome:
  - Success returns the player to the library with the tome.
  - Failure returns the player to the library without completing the request.
  - No permanent penalties yet.
- Save state:
  - Persist whether the request is incomplete or complete.
  - Persist whether the recovered tome appears in the archive.

## UX/Input

- Keyboard and mouse controls for movement, card selection, card activation, and interaction.
- Controller support is optional in `0.1`, but input actions should be mapped through Godot input actions rather than hardcoded keys.
- The hub must show interact prompts for the desk, shelf, and entrance.
- The dive UI must show health, current cards, card costs or cooldowns, and current objective.
- Tooltips or concise help text must explain the active request and each starter card.
- The player must always know whether they are in hub mode or dive mode.

## Content Scope

- One library room.
- One visitor request.
- One tome reward.
- One starter deck of 5-7 cards.
- At least three mechanically distinct starter card verbs.
- Two enemy types at most.
- One hazard type.
- 5-7 dungeon room templates.
- Placeholder art, UI, audio, and VFX are acceptable if readability is strong.

## Technical Notes

- Use Godot scenes for hub, dungeon rooms, enemies, cards, interactables, and UI panels.
- Define cards, room templates, enemies, and requests as external data resources or data files where practical.
- Keep the dungeon generator simple: select required room templates, connect them in a readable path, and ensure the tome room is reachable.
- Separate persistent library state from transient run state.
- Avoid implementing broad meta progression or content authoring tools; leave clean seams for them.
- Treat the starter deck as invalid if it cannot produce movement, defense, and offense within the first dive.

## Acceptance Criteria

- The game launches into the library without manual setup.
- The player can read the active request, enter the dungeon, complete a short dive, recover the tome, and return.
- At least three starter cards are mechanically distinct and useful during the dive.
- A typical combat room should present at least one meaningful card decision within a short encounter.
- Dungeon rooms are not a single static map; at least room ordering or room selection varies between runs.
- Success visibly completes the request and adds the tome to the archive.
- Failure leaves the request incomplete and allows the player to try again.
- The game can be closed and relaunched with completed request and archive state preserved.
